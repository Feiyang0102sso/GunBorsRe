# 敌人扎堆：原版群体移动调查与阶段方案

后续更正：本文件记录的 35 敌人试验沿用了重建版错误的默认容量 50。原版默认敌人池容量为 20，已在后续阶段修复，详见 [刷怪容量调查](spawn-budget.md)。分离算法和此前测得的压力测试结果不变，但 35 敌人不再代表默认玩法应有的人数。

## 用户反馈与范围

寻路缓存优化后帧率恢复，但 pack7 / map6 第 50 波出现大量敌人模型互相重叠。用户提供的原版照片中，追击者通常保持一定间距，呈队列或小群靠近。照片不是相同时间、相同刷怪状态，不能由可见数量直接反推出原版刷怪上限或编队参数。

电雷多次电击的实测反馈已收到，本阶段不更改手雷行为。

2026-09-13 补充：用户观察到不同种类的敌人近乎同时成组出现，随后呈队列或小群，怀疑从预选阵容中随机选择；原版偶尔也有两个敌人贴得很紧。将这些作为待核对的现象，不预先设定固定编队或强制最小间距，一切以原版执行链与 BIG 为准。

## 刷怪与分组的补充核对

- `CEnemySpawner::UpdateRules :146903` 顺序处理最多十条启用的规则；`UpdateRule :146849` 分别按资源、间隔、数量与上限生成敌人，一条规则一次更新最多补刷两次。不同种类接近同时出生与此机制相容，但是否由当前生存关卡脚本同步启用，仍须跟踪该关卡 Flow。
- `ExecutePacket :146948` 每个出生包绑定并生成一个敌人；这里的 Packet 不能解释成一组敌人或预设阵容。
- `GetSpawnPointSpecific :146576` 在启用节点中随机取一个出生点；`SpawnEnemyPath :146518` 还支持指定节点和路径。这些入口本身没有显示持续队列槽位。
- 地图确实有 `spawnTag` 和 `CLayerObject::SpawnTagGroup :126418`：按标签激活地图预置实例。`maps/map.bt` 的 `ObjectInstance`、`ObjectExtra` 包含敌人类型，所以不能将它一概归为场景装饰；也不能仅凭这个字段就认定第 50 波使用它生成预选阵容。需要核对实际地图实例和关卡脚本调用。
- 因此，已确认的近邻分离与尚待确认的出生编组分别记录。不能由 `CFlock` 不按组过滤，推导出整个原版不存在编组机制。

## 已确认的原版执行链

来源均为 `_prep/_IDA_OUT/gunbros_3.6.0_IOS.c`：

1. `CLevel::AddObject :116854` 把类型为敌人的对象加入关卡敌人列表。
2. `CLevel::Update :121318` 在对象更新前调用 `CFlock::Refresh`。
3. `CFlock::Refresh :170467` 先刷新距离表，再调用 `RefreshFlock`。
4. `CFlock::RefreshFlock :170259` 对关卡敌人列表中的位置计算分离向量。对不同对象、距离平方不超过 10000 的邻居，累加 `(自身位置 - 邻居位置) × 1000 / 距离平方`；完全同坐标时该邻居贡献为零。这些数值属于原程序算法常量，不是手填资源表，也不表示固定最小站距。
5. `CEnemy::UpdatePathFinder :70068` 取得该敌人的分离向量，在后续分支中与路径移动速度合成，再按移动速度上限限制最终速度，最后乘时间步更新位置。

原版分离计算遍历的是关卡敌人列表，这段代码没有按同次出生批次或敌人种类分组。刷怪批次与持续保持间距应分别追踪。

## 当前实现差异

- 当前没有 `CFlock` 实现，也没有在 `CombatScene` 的敌人移动前刷新近邻分离向量。
- `EnemyCombat.cpp` 的追击分支直接朝目标或导航路点移动；多人共享目标时可以逐渐重合。
- 上轮 `ILayerPath` 查询缓存没有修改出生数量或直接调整移动方向。既有 1200 步 A/B 对照验证了当时记录的状态一致，但不是本次 pack7 场景与原版间距一致的证据。

## 阶段方案与任务

1. 核对原版 `UpdatePathFinder` 的速度合成、夹角分支、到达目标后的行为及参与分离的对象生命周期；有反编译歧义时回查 ARM 指令。按涉及的资源读取同时核对 map.bt、enemy_template.bt 和 Flow 模板。
2. 恢复对应职责的 `CFlock` 分离计算。每个逻辑步统一读取敌人位置快照，避免前面的敌人移动后影响后面的计算顺序。
3. 在已核对的路径移动分支接入原速度合成与限速，保留上轮寻路缓存。不凭截图设固定间距，不用按敌人 ID 的特例补丁。
4. 用原 BIG 实体建立移动回归：邻近追击、同向队列、绕圈聚怪、窄通道、死亡移除和出生加入；核对原版完全重合时的零贡献，不能凭经验编造随机推开。
5. 在 pack7 / map6 第 50 波固定随机种子，记录最近邻距离、重叠情况、出生数、击杀数和帧耗时；同时检查第 50 波原性能场景，避免恢复间距后重新卡顿。

验收目标是按原算法恢复邻近敌人的分离作用及移动行为，不承诺任何情况下绝不重叠，也不将单张截图的排列当成固定阵型。

## 2026-09-13 实施与试验结果

用户已授权本轮试验和修复，并澄清预选阵容只是外观猜测。本轮没有引入编队状态或修改刷怪数量、节点选择、时间规则。

### 补齐的原版依据

- `CEnemy::UpdateBehaviour :70851` 只有模式 0 和 2 调用 `UpdatePathFinder`；模式 1 和 3 使用 `UpdateGotoPoint`。分离只接入追击与链接路径，不无条件移动静止、眩晕或直线移动的敌人。
- 直接读取 `_prep/gunbros` 的 ARMv7 切片及符号，反汇编 `CEnemy::UpdatePathFinder`（0x3cf04）。0x3d0c8—0x3d1bc 对应速度合成；原程序地址 0x3c406c 的浮点值为 +1，0x3c4078 为 pi（0x40490fdb）。对于有限向量，夹紧后的 acos 减 pi/2 不大于 pi/2，实际选择向量相加，再限速。证据保存在 `obj/flock-arm.txt`，读取脚本在 `obj/inspect_flock_arm.py`。
- `CLevel::RemoveObject :116802` 才从敌人列表移除对象。因此未移除的尸体仍参与邻居计算，未按死亡、敌人种类或目标类型另作过滤。
- `CLinkPathFinder::Update :168635` 原版本身使用精确到点判断，本轮未发明到点半径。清空邻居作用的真实敌人沿路到点、once 模式结束已回归；拥挤链接路径在所有地图中的行为仍未穷举。
- 已查 `big_assets/enemy_template.bt`、`maps/map.bt`、`entries/common.bt`、`flow_bytecode.bt` 与 `flow_native_sources.bt`；没有修改资源读取器。

### 实现

- `CFlock.h/.cpp` 恢复原近邻公式。`CombatScene` 在敌人更新前统一计算，各敌人的本步向量缓存在 `EnemyCombat`。复用指针列表容量，每步不分配距离矩阵。
- `CEnemy::UpdatePathFinder` 合成路点速度与分离向量，并限制到脚本变量 0 的速度；到达距离仍用于停止判定，步长按原函数朝路点限制。
- 保留原版零距离贡献为零的情况。没有硬碰撞排斥、固定最小间距、按 ID 特例或随机抖动。
- Debug 保留 `--flock-check`、`--flock-performance-check` 和试验开关 `--disable-flock`；Release 不包含测试开关。

### 复现与 A/B

最小回归使用真实 BIG 敌人，先完成出生动画，再隔离追击原生行为。初始间距 20，60 个 16 ms 更新后：修复前 17.122，修复后 58.641；两者继续前进，修复前退出码 1，修复后 0。日志 `obj/flock-before.log`、`obj/flock-after.log`。20 是测试输入，不是游戏最小间距。

第 50 波：pack7 / map6，从用户位置 733.6 / 284.1 开始，固定随机种子和四段移动输入，不射击、玩家无敌、无兄弟，运行 1200 个 16 ms 更新。对照只切换分离，使用同一个修复后的测试程序。
